# 契約実績LPから抽象化した品質標準（検証用）

> **機密配慮**: 実案件の店舗名・写真・ロゴ・原稿・料金・URL・顧客コメント・デザイン完成物はこのPublicリポジトリに保存しない。以下は汎用の制作原則のみ。使用前に店舗個別の情報と許諾を確認する。

## 1. 参考資料の分類

| 入力資料 | どう扱うか | 自動確定してよいか |
|---|---|---|
| 店舗から提供された写真・ロゴ | 原本の出所、著作権・肖像・媒体・加工範囲を素材別に登録 | **不可**。「提供された」は「LP掲載可」ではない |
| 制作途中のスクリーンショット | 情報階層、構図、コピー配置、レスポンシブの設計参考 | **不可**。完成品質の保証ではない |
| 完成に近いスクリーンショット | 文字・余白・写真・訴求・CTAの視覚QA例 | **不可**。事例のデザインを他店にコピーしない |
| 要件・デザイン定義書 | 確認質問、章立て、業務停止条件の参考 | **不可**。参考店舗の事実を転用しない |

## 2. 来店・問い合わせにつながる情報設計

ユーザーに不安を与えず、**その店舗に固有の良さが伝わる**ことを目標とする。
基本候補は **第一印象と価値提案 → 対象客の不安 → 選ばれる理由 → 商品・サービス → 店舗実写・根拠 → 料金・初回利用 → アクセス → 正式な予約・相談方法**。
ただし全部を同じ順序で並べない。店舗の業種、公開可能な素材、最重要顧客行動、1ページの情報量で構成を組み替える。

- コピーは「自分に関係がある」「なぜここなのか」「どう利用するか」が一読で分かるようにする。根拠のない健康効果、実績、推薦、絶対表現は出さない。
- 価格、メニュー、所要時間、初回条件、税区分、季節限定条件は正本の出典と確認日を付ける。最新性不明なら掲載・公開を止める。
- 初回にありがちな不安（予約の要否、当日の流れ、支払方法、キャンセル条件等）は確認済み項目のみ記載する。
- CTAのボタン名は実際に可能な行動と合わせる。予約不可なら「今すぐ予約」としない。正式なリンクがない場合、押せるボタンに偽URLを入れない。
- 「良さそう」だけで終わらないよう、最終行動をページ上部・料金・最終案内に整理する。ただし過度な煽りを避ける。

## 3. 実写真中心のアートディレクション

素材ごとに「画像ID／ファイルの保管先／撮影・提供元／権利者／撮影・提供日／許諾の証跡／利用媒体／加工許可／人物の同意／掲載期限／掲載セクション／PCとSPのトリミング」を台帳に記録する。

- Hero：主役を明瞭にし、コピーが読める構図。PCとSPで別の焦点・比率も検討する。
- サービス：何を受けられるかが伝わる実施場面。架空の施術・設備や成果を示さない。
- 初回来店：実際の案内・接客・導線があれば安心感を補う。
- 空間：実際に来店した際の雰囲気と設備が分かるものを優先する。
- 使用不可素材：権利不明、第三者の無許可転載、人物の同意不明、確認のないAI生成写真。
- 参考画像：レイアウト比較に限り、実店舗の証拠写真や公開素材と混同しない。

## 4. デザイン・実装に求めるもの

- ブランド固有の視覚設計。参考LPの配色、署名モチーフ、文言、画像配置を一律転用しない。
- DesktopとMobileの両方で Hero／価格／初回来店／予約導線が読めること。320/375/390pxで確認。
- Heroの実写の主役が文字やスマホのクロップで見切れないこと。
- 適切なH1/H2、代替テキスト、focus-visible、キーボード、コントラスト、200%ズーム、400%リフロー、reduced-motionを確認。
- 画像の容量・読み込み速度、ページ内リンク、外部公式リンク、未接続CTA、表示欠落、文字の重なりを確認。
- 営業用サンプルと正式公開を区別し、承認なしに顧客送信・SNS掲載・GitHub Pages公開をしない。

## 5. AI生成に対する検査と判断

ローカルQwen3 8Bは、要件・デザインのドラフト作成を補助するだけで、店舗事実の確認、画像ライセンス照合、購入・予約率の測定、実機スクリーンショット検査はできない。

`detail_pipeline.py` の新機能：

1. 各章生成のプロンプトに**汎用品質基準**を加える（実店舗情報をプロンプトに含めない）。
2. AIの既存2ロール自己レビューにも品質基準を反映する（レビュー回数は増やさない）。
3. 保存済み要件ドラフトを `--audit-existing` でAIなしに再監査しても、同じ品質チェックを出力できる（ドラフト本文は変更しない）。
4. 要件・デザインのドラフト出力時に `requirements_reference_qa.json`／`design_reference_qa.json` を作る。
5. JSONは話題の出現と**人間レビュー項目**のみ。キーワードが現れても「品質合格・画像許可・成約効果・公開許可」と判定しない。
6. 既存の出典監査・要件ハッシュ承認・架空案件限定・ローカル保存・公開禁止を維持する。

## 6. 次のステップ（別工程）

実案件対応には、正本となる素材台帳・出典付き事実台帳・許諾記録を機密領域で扱う機能、画像／動画の構図QA、実装後のスクリーンショット比較、実サイトのリンク・コンバージョン計測が別途必要。現在の架空専用パイプラインでは**未実装**であり、追加承認なしに実店舗データを流さない。

## 7. 検証コマンド

ローカルでリポジトリのファイルを取得した場合、Ollamaに接続せず構造テストを実施：

```bash
cd automation/local-ollama
python3 -m unittest test_detail_pipeline -v
```

本書と生成プログラムを検証しただけでは、実際のLPの完成品質を保証できない。
### 既存の検証用ドラフトに対する軽量チェック

```bash
python3 "$HOME/Downloads/misemiru_detail_pipeline.py" --audit-existing
```

Qwen3の生成を始めない。既存の要件ドラフト本文は書き換えず、ローカルの品質JSONと過去QAのバックアップを更新する。**公開・顧客送信・Sheets書き込みは一切行わない**。
